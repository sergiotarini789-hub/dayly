# Dayly Logical Database Architecture

**Phase:** 0C — Domain Model & Database Architecture
**Status:** In progress
**Related documents:** [`DOMAIN_MODEL.md`](DOMAIN_MODEL.md), [`DATA_OWNERSHIP.md`](DATA_OWNERSHIP.md), [`DATA_LIFECYCLE.md`](DATA_LIFECYCLE.md), [`DATA_CONSTRAINTS.md`](DATA_CONSTRAINTS.md)

> This is a logical persistence blueprint. It intentionally does not contain SQL, DDL, migrations, executable policies, table creation, or application code. The word “record” means a conceptual persistence unit, not an instruction to create a physical table now.

## 1. Architecture goals

The eventual PostgreSQL/Supabase implementation should be:

- user-isolated by construction;
- normalized around source-of-truth domains;
- explicit about one-to-many and many-to-many relationships;
- precise about instants, local dates, time zones, and recurrence;
- able to query Today, Tasks, Projects, Calendar, Habits, Focus, Notifications, and Search efficiently;
- conservative about derived data and cached projections;
- extensible for provider-neutral integrations without placing provider fields in core Dayly entities;
- evolvable through additive migrations.

The MVP should favor a small set of durable records over a generalized event-sourcing or integration platform.

## 2. Logical persistence conventions

### 2.1 Identifiers

- Every user-owned logical record has a stable opaque identifier.
- Identifiers are generated by the persistence boundary and are not meaningful business values.
- External provider identifiers are stored separately from Dayly identifiers and are scoped by provider/account/calendar as appropriate.
- Relationships use stable identifiers rather than titles or timestamps.

### 2.2 Ownership

Every Dayly-owned record must have a reliable path to exactly one User. For simple records this is a direct owner reference. For child records, the owner can be checked through the parent, but a direct owner reference may still be useful for RLS and high-frequency queries. The physical implementation must choose one consistent strategy and enforce it.

No relation may connect records belonging to different Users. Provider-owned records are visible only through the User's authorized Integration Connection.

### 2.3 Timestamps and time

- Instants such as creation, update, completion, focus start/end, and synchronization time are stored with unambiguous instant semantics.
- Local recurring intent preserves an IANA time-zone identifier or equivalent supported zone reference.
- Date-only deadlines and all-day events are not represented by silently treating local midnight as a universal instant.
- User-facing dates are interpreted in the relevant User, Habit, Event, or provider time zone.
- Every mutable record has a creation and update moment conceptually; milestone moments such as completion or archive are explicit when needed.

### 2.4 Mutable versus derived values

A field belongs on a source record only when the user or owning domain needs to set it and it cannot be safely recomputed from another source. Counts, progress percentages, streaks, overdue flags, Today membership, and search matches are derived unless a later performance decision justifies a cache.

### 2.5 Enumerations and extensibility

Statuses and kinds need a documented vocabulary, but a physical implementation should avoid making an unresolved product decision irreversible. Stable MVP values can use constrained reference values; future values require an additive migration and UX decision.

## 3. Logical record inventory

### 3.1 Identity and preference records

| Logical record | Cardinality | MVP role |
|---|---:|---|
| User principal | one per ownership principal | Required ownership boundary; authentication implementation is out of scope. |
| Account link | future one or more per User | Reserved for authentication/recovery providers; not a productivity record. |
| Profile | zero or one per User | Display name and explicitly supported personal presentation. |
| User Preferences | one per User | Locale, default time zone, planning defaults, appearance, and notification defaults. |
| Availability Rule | zero or more per User | Recurring planning availability. May be represented within preferences initially. |
| Availability Exception | zero or more per User/rule | Date-specific overrides; future if needed. |

### 3.2 Core Dayly records

| Logical record | Cardinality | MVP role |
|---|---:|---|
| Project | zero or more per User | Outcome container for Tasks. |
| Task | zero or more per User | Actionable work. |

| Task-Tag association | zero or more per Task/Tag | Many-to-many labeling relationship. |
| Task Schedule Block | zero or more per Task | Planned work interval. |
| Calendar Event | zero or more per User | Dayly-owned time-bound commitment. |
| Habit | zero or more per User | Recurring behavior definition. |
| Habit Occurrence | zero or more per Habit | Materialized expected/completed/missed occurrence. |
| Focus Session | zero or more per User | Actual effort record. |

| Notification | zero or more per User | In-product reminder/system item and handling state. |

### 3.3 Future integration read records

| Logical record | Cardinality | MVP role |
|---|---:|---|
| Integration Connection | zero or more per User | Future consent and connection boundary. |

No future integration record is required to use the MVP core.

## 4. Core logical record attributes

The following attributes are conceptual. Names, physical types, nullability syntax, and exact column strategy belong to a later implementation decision.

### 4.1 User principal

- stable identifier;
- lifecycle/deletion state;
- created and updated moments;
- optional last-active metadata if justified.

Authentication secrets, provider tokens, and recovery data do not belong in this Dayly domain record.

### 4.2 Account link

Future conceptual attributes:

- stable account-link identifier;
- User relationship;
- provider/type;
- provider subject/reference;
- account status;
- created/updated moments;
- revoked/deleted moment where applicable.

The account link must not become the owner reference for Tasks; User remains the ownership principal.

### 4.3 Profile

- User relationship;
- display name;
- optional avatar/reference metadata only if approved;
- created/updated moments.

Locale and time zone belong to Preferences unless a later product decision establishes them as identity/profile values.

### 4.4 User Preferences

- User relationship;
- locale;
- default IANA time zone;
- preferred week/day display defaults;
- planning defaults;
- notification defaults/quiet hours;
- appearance preferences;
- created/updated moments.

Sensitive provider credentials and source health do not belong here.

### 4.5 Availability Rule and Exception

An Availability Rule conceptually contains:

- User relationship;
- recurring day/pattern;
- local start/end window;
- applicable time zone or inheritance from User Preferences;
- enabled state;
- created/updated moments.

An Availability Exception conceptually contains:

- User/rule relationship;
- local date or time range;
- availability override;
- reason/label only if useful;
- created/updated moments.

If MVP planning can use a single simple schedule, these may begin as a structured preference value. They must still retain semantics that can expand to exceptions later.

### 4.6 Project

- User owner;
- name;
- outcome/description;
- priority if supported;
- target date/context if supported;
- lifecycle state, initially active/archived;
- created, updated, archived moments;
- optional ordering/display metadata only if the list needs it.

Do not store a project progress percentage as a source value. Project progress is derived from Tasks and the later formula.

### 4.7 Task

Conceptually evaluate these properties:

- stable identifier;
- User owner;
- optional Project relationship;
- optional parent Task relationship;
- title;
- description;
- canonical lifecycle status;
- priority;
- deadline with date/time precision and time-zone semantics;
- estimated duration;
- completion moment;
- archive moment;
- creation/update moments;
- optional ordering within a Project or parent;
- optional triage metadata only after Inbox rule is decided.

Not stored directly on the Task by default:

- one scheduled time, because a Task can have zero or many Schedule Blocks;
- actual duration as an independently editable counter, because Focus Sessions are the evidence source;
- overdue, scheduled, planned, or Today flags, because they are derived;
- a duplicate Project name or Tag name;
- provider event identifiers.

The product-level `actual_duration` property is represented by an aggregate of eligible Focus Sessions. A later manual-correction capability may add an explicit adjustment record rather than overwriting the aggregate silently.

### 4.8 Task-Tag association

- Task relationship;
- Tag relationship;
- User ownership validation path;
- assigned moment if history is useful.

The relationship does not require a separate user-facing object.

### 4.9 Tag

- User owner;
- normalized name for uniqueness;
- display name;
- created/updated moments;
- optional archived/deleted marker if tag cleanup is supported.

Tag names must not be globally unique across all Users.

### 4.10 Task Schedule Block

- stable identifier;
- User ownership path;
- Task relationship;
- start instant/local planning representation;
- end instant/local planning representation;
- relevant IANA time zone or inherited planning zone;
- planned/removed state if current-state management requires it;
- created/updated moments;
- optional reschedule metadata only if later analytics requires plan history.

A Schedule Block does not store Focus actual duration and does not carry a Calendar Event provider ID. The physical model should support zero-to-many blocks per Task even if the MVP editor initially creates one at a time.

### 4.11 Calendar Event

- stable identifier;
- User owner;
- title;
- notes/description;
- start and end representation;
- all-day flag and local date semantics;
- IANA time zone;
- location text if supported;
- recurrence definition and exception references if supported;
- lifecycle state such as active/cancelled under the later event policy;
- created/updated moments;
- optional deliberate linked Task relationship, if the product chooses to support it.

A Dayly Calendar Event is never an implicit Task Schedule Block. If an event is linked to a Task in the future, the link is contextual and does not merge the records.

### 4.12 Habit

- stable identifier;
- User owner;
- name and optional description/context;
- recurrence rule representation;
- preferred local time/context;
- IANA time zone or inherited zone;
- lifecycle state, initially active/archived with paused behavior reserved;
- created/updated moments;
- archived/paused moment if supported.

A Habit stores the rule, not a precomputed lifetime streak or an unbounded set of future occurrences.

### 4.13 Habit Occurrence

- stable identifier;
- User ownership path;
- Habit relationship;
- occurrence key/date and expected local window;
- relevant time zone/rule version context;
- occurrence status, initially expected/completed/missed;
- completed moment and completion source if needed;
- created/updated moments.

The occurrence key must prevent two materialized records from representing the same Habit occurrence. Future skipped/suppressed/backfilled states require explicit product decisions.

### 4.14 Focus Session

- stable identifier;
- User owner;
- optional Task relationship;
- optional Project relationship when no direct Task context is used;
- session status;
- started instant;
- ended instant when finished;
- accumulated paused duration or pause facts;
- actual duration at completion or a derivation rule;
- interruption note/metadata if supported;
- created/updated moments.

Recommended context rule: a session has either a direct Task, a direct Project, or no context. If Task is present, Project context is derived from the Task rather than duplicated. Orphan sessions with no context are valid.

### 4.15 Reminder Rule

- stable identifier;
- User owner;
- typed source relationship to a Task, Calendar Event, Habit/Occurrence, Focus Session, or approved system condition;
- trigger definition;
- local time-zone semantics;
- enabled/disabled state;
- next trigger/last handled metadata where needed;
- created/updated moments.

The physical implementation should use enforceable source relationships rather than an unconstrained arbitrary ID if the MVP only supports a small number of source types.

### 4.16 Notification

- stable identifier;
- User owner;
- optional Reminder Rule relationship;
- source reference/type for navigation;
- notification kind;
- available/scheduled moment;
- read/handled moment;
- dismissed/snoozed state and time where supported;
- created/updated moments;
- optional stale/error context for integration notices.

Delivery attempts, push tokens, email provider responses, and retry queues are not MVP records.

## 5. Future integration logical records

### 5.1 Integration Connection

- User owner;
- provider key, such as Google Calendar or NutriTrack;
- external account reference;
- connection status;
- consent/scope representation;
- last successful synchronization moment;
- last attempted synchronization moment;
- error/stale state;
- created/updated/disconnected moments.

Provider tokens/secrets belong in the secure integration boundary, not in ordinary user-readable domain records.

### 5.2 External Calendar

- Integration Connection;
- provider calendar identifier;
- display name;
- selected/sync-enabled state;
- provider time-zone metadata;
- provenance and last-seen moment.

### 5.3 External Event

- Integration Connection and External Calendar;
- provider event identifier and stable occurrence identifier where required;
- title/summary and optional description/location;
- provider start/end/all-day/time-zone representation;
- recurrence/provenance metadata;
- provider revision/etag if useful for future conflict handling;
- source lifecycle state, such as active/deleted/stale;
- last synchronized moment.

External Event is a read model. It must not become a Dayly Calendar Event merely because it is displayed in Calendar.

### 5.4 External Data Snapshot

- Integration Connection;
- source category/metric key;
- source period and source update moment;
- normalized read-only value/summary representation;
- provenance and freshness;
- consent/scope reference;
- imported/cache moment;
- stale/invalid state.

The shape of the nutrition payload and metric keys is intentionally deferred to the NutriTrack contract.

## 6. Task and relationship model

```text
User
 ├── owns Project (0..many)
 ├── owns Task (0..many)
 │    ├── belongs to Project (0..1)
 │    ├── has parent Task (0..1)
 │    ├── has child Tasks (0..many; one level in MVP)
 │    ├── has Tags (0..many through association)
 │    ├── has Schedule Blocks (0..many)
 │    ├── has Reminder Rules (0..many)
 │    └── has Focus Sessions (0..many)
 └── owns Calendar Events, Habits, Focus Sessions, Notifications
```

### MVP task relationship decisions

- A Task belongs to zero or one Project. Multi-project membership is not required and should not be inferred.
- A parent Task relationship is optional. MVP should support one child level; deeper nesting is deferred.
- A Task has zero or many Schedule Blocks logically; the first UX may make one active block easiest to create.
- A Task's actual duration is a read aggregate of completed Focus Sessions, not a second mutable truth.
- Tags are many-to-many but only Task tagging is in current MVP scope.

## 7. Derived data architecture

### 7.1 Default rule

Compute derived concepts from source records at read time or in a controlled read model. Do not persist a derived value merely because it appears as a card or screen.

### 7.2 Optional caches

If query cost later requires caching, a cache must include:

- source period and time zone;
- calculation/version identifier;
- generated/freshness moment;
- a clear rebuild path;
- no independent user-editable meaning.

A stale cache must never override current source records without a visible freshness policy.

### 7.3 Search

For MVP, search should use PostgreSQL-native text matching over Tasks and Projects, with normalized title/description/project context and appropriate database indexes when implementation begins. An independent Search Index record or dedicated search engine is not required initially.

When Habits, Calendar, future Notes, external provenance, or complex ranking are added, a derived search projection may be introduced. It remains rebuildable and never becomes the source of truth.

## 8. Query-oriented logical views

These are useful future read queries, not source records:

- Today task queue;
- Today agenda;
- active project task list;
- upcoming tasks by deadline;
- schedule blocks by time range;
- calendar events by range;
- habit occurrences by date range;
- focus sessions by Task/Project and time range;
- unread/actionable Notifications;
- weekly/monthly Analytics summaries;
- external events by connection/calendar and range.

## 9. Physical implementation guardrails for a later phase

- Keep source aggregates separable even if a UI response joins them.
- Do not use polymorphic unvalidated identifiers for core relations when a constrained relation is possible.
- Keep provider-specific fields in integration read models rather than Task, Calendar Event, or Habit records.
- Treat recurrence and time-zone data as domain values requiring explicit parsing/validation.
- Add physical indexes only for measured query patterns listed in [`DATA_CONSTRAINTS.md`](DATA_CONSTRAINTS.md).
- Design RLS before exposing any record to a client.
